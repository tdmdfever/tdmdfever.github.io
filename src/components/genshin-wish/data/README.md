# Precomputed odds for the home-page Genshin widget

Nothing in the browser computes these. `odds-base.json` and `odds-extras.json` are
generated by running the real calculator engine (`exactEngine.ts`, the one the live app
runs) for every starting state and goal combination the widget offers, then encoding the
curves compactly (see `../codec.ts`). The generated files are committed; the build and CI
never run the generator.

Provenance: the source repo, its commit hash, the date and the storage precision are in the
`meta` block at the top of `odds-base.json`.

Regenerate with `npm run sync:genshin`. It needs the calculator repo checked out next to
this one (`../genshin-wish-calculator`), runs the engine under `tsx` (fetched by `npx` on
first use), and takes about 3 minutes on 8 cores. The output is deterministic. It aborts
without writing anything if the engine's shared-prefix assumptions or the encode/decode
round trip fail.

## What is in the tables

Index = `pity * 2 + (guaranteed ? 1 : 0)`, pity 0-89. Every curve has one value per pull, 0-300.

Naming: the tables and generator call the goals 5★ A, 4★ A and 5★ B. On screen the widget
calls them "First 5★", "4★ to C2" and "Second 5★" (see `GOAL_NAMES` in `../odds.ts`).

| File | Key | Contents |
| --- | --- | --- |
| `odds-base.json` (bundled) | `A` | 5★ A alone: chance of the featured 5★ by each pull |
| `odds-extras.json` (fetched after mount) | `A4` | 5★ A then a 4★ A to C2 (the 4★ is anchored to 5★ A's banner) |
| | `AB` | 5★ A then a second, sequential 5★ B |
| | `A4B` | all three, in that order |
| | `barsA4`, `barsA4B` | chance of owning at least C0..C6 of the 4★ by each pull, for `A4` / `A4B` (7 series joined by `;`) |

Each curve is the cumulative chance of finishing that goal AND every goal before it (a
"prefix" of the plan), which is how the calculator reports a goal list. The prefix curves
are shared between combinations (5★ A is identical in all four; "A then 4★" is identical
with or without 5★ B after it), so each is stored once; the generator asserts this to 1e-9
before writing. The bar tables are not shared: once a plan moves on to 5★ B the 4★ stops
accruing copies, so `A4` and `A4B` differ (by up to ~39 points).

Storage precision: curves to 0.001 percentage points, bars to 0.01. A displayed value can
differ from the engine's unrounded one only in the last shown digit. A value that is not
certain is never stored as exactly 100% (it is kept one step below), so the widget never
shows "100%" for a chance that is really 99.99%.

## Assumptions baked in

Character banner, Capturing Radiance model A (crCounter 0, r2TotalWinRate 0.55, the
calculator's defaults), 4★ pity 0, no weapon banner, budget 300. 4★ pity has no effect on
5★ odds (measured under 3e-14). Capturing Radiance is speculative (the real mechanic is
undocumented) and only matters after two lost 50/50s in a row, which the widget does not
ask about.

## Engine facts worth knowing

- 5★ rate on the nth pull since the last 5★: 0.6% up to n=73, then +6% per pull (6.6% at 74,
  96.6% at 89), 100% at 90. The widget reads these constants from `meta.pity`.
- A 5★ is featured 50% of the time; a loss makes the next 5★ certain to be featured. The
  single-goal curve is certain by pull 180 from any start.
- Floats: the engine can return a value fractionally above 1 (1.0000000000000073); the
  generator's encoder clamps to [0, 1]. Never compare a probability with `=== 1`.
- **Known approximation.** For the three-goal plan (5★ A, 4★ to C2 anchored to it, then 5★ B)
  the third curve comes from the calculator's between-phase handoff, which averages over when
  the previous phase ended. Against an independent Monte Carlo run (200k-400k trials) it was up
  to ~9 percentage points off at some pull counts (the true curve is lumpier), while every
  other curve here agreed within sampling noise (under ~0.3 points). The live calculator shows
  the same numbers, so the widget matches it, and shows a note when this plan is selected.
  For this plan the engine's output also depends slightly on the pull budget it is run with
  (the tables here are one 300-pull run, sliced): against the live calculator computing fresh
  at the shown budget, the third curve differed by up to ~0.9 points and the constellation bars
  by up to ~3 points. For the other three plans the widget matched the live calculator to its
  display rounding.
  See ARCHITECTURE.md "Known limitations" in the calculator repo.
